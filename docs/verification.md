# Проверка Poknite

Это руководство описывает проверку совместимости, доставки и потребления ресурсов перед выпуском. Результаты зависят от сборки, операционной системы, устройства и сети. Целевые показатели ниже служат критериями проверки и не являются гарантией для любой среды.

## Автоматические проверки

Установите зависимости сборки из [руководства сборки](building.md) и выполните из корня репозитория:

```sh
cargo fmt --all -- --check
cargo test --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo build --workspace --release --locked
python3 tools/check_sizes.py
python3 tools/client_smoke.py
python3 tools/tls_smoke.py --binary target/release/poknited
```

Сетевые сценарии требуют Python 3 и OpenSSL. Они запускают отдельный сервер с временной базой и сертификатами. `client_smoke.py` создаёт ключ на устройстве, переносит его между тестовыми профилями локально и проверяет зашифрованную доставку через HTTPS/WSS, восстановление, TTL и отзыв. `tls_smoke.py` проверяет сертификаты, их замену без разрыва соединений и ошибки конфигурации. Синтетические `tls_smoke.py`, `server_soak.py` и `disk_full.py` явно используют `e2ee_required=false` только в своей временной конфигурации: их результаты не измеряют клиентскую криптографию или размер зашифрованной нагрузки.

Тесты Rust проверяют сохранение до подтверждения, повтор отправки, независимые позиции устройств, приглашения, права на каналы, ограничения текста и хранилища, истечение сообщений и восстановление соединений. Команды Android приведены в [руководстве клиента](../android/README.md#тесты).

CI проверяет сборки Linux, Windows и Android. Успешная компиляция и тесты в CI не заменяют проверку уведомлений, фонового режима и энергосбережения на целевых устройствах.

## Ресурсные бюджеты

МиБ равен 1 048 576 байтам. Размер исполняемого файла и размер загружаемого архива фиксируйте отдельно.

| Компонент | Размер сборки | Память |
| --- | ---: | ---: |
| Сервер | ≤10 МиБ | RSS ≤32 МиБ при 60 ожидающих соединениях |
| Windows/Linux | ≤12 МиБ | RSS ≤25 МиБ в фоне, ≤50 МиБ с окном |
| Android | Подписанный APK ≤5 МиБ | PSS ≤70 МиБ с включённым приёмом в фоне |

При каждом измерении записывайте версию или commit, профиль сборки, архитектуру, ОС, оборудование, длительность и условия нагрузки. Для памяти используйте release-сборки без отладчика; фиксируйте начальное, установившееся и максимальное значения. RSS и PSS — разные показатели, их нельзя напрямую сравнивать.

В установленный объём включайте исполняемые файлы, конфигурацию и собственные зависимости. Отдельно указывайте системные библиотеки, данные приложения и временные журналы SQLite. Для Linux учитывайте библиотеки X11, fontconfig/freetype, D-Bus и потребность в XWayland. На Android указывайте объём пакета и пользовательских данных отдельно.

Основная база сервера по умолчанию ограничена 32 МиБ, история клиента — 8 МиБ и 1000 сообщениями. Эти пределы не включают журналы SQLite, конфигурацию и диагностические логи. Проверяйте их размер отдельно и после завершения нагрузки.

## Сервер и доставка

Для прогонов требуется release-файл сервера. Следующие команды создают временную отдельную базу и подключают 60 устройств:

```sh
mkdir -p /tmp/poknite-verification
python3 tools/server_soak.py --binary target/release/poknited \
  --devices 60 --duration 86400 --idle \
  --report /tmp/poknite-verification/idle-24h.json
python3 tools/server_soak.py --binary target/release/poknited \
  --devices 60 --duration 86400 \
  --report /tmp/poknite-verification/delivery-24h.json
```

Сравните память, загрузку CPU, количество соединений, размер базы, SQLite-журналов и логов в начале и конце суток. После нескольких циклов хранения размеры должны стабилизироваться. Проверьте отсутствие пропущенных доставок и повторных записей у получателей. Короткий прогон полезен для поиска регрессий, но не подтверждает суточную стабильность.

Нагрузочный сценарий измеряет локальное соединение. Для целевого p95 ≤2 секунд повторите измерения через HTTPS/WSS на фактическом сервере и клиентских сетях. Считайте задержку от принятия отправки сервером до получения сообщения клиентом; отдельно измеряйте время до системного уведомления. Укажите размер выборки, частоту сообщений, RTT, потери сети и метод синхронизации часов.

Обязательные сценарии доставки:

- Телефон и компьютер одного пользователя получают сообщения независимо.
- Повтор отправки после потери ответа возвращает прежнее сообщение без создания второй записи.
- После обрыва соединения и перезапуска сервера восстанавливаются ещё доступные сообщения.
- После истечения срока сервер не выдаёт сообщение, а ранее полученная локальная копия остаётся.
- Отзыв устройства закрывает действующий поток и отклоняет последующие подключения.
- Чужой канал, истёкшее приглашение и превышение 4 КиБ UTF-8 отклоняются.
- Медленный клиент переподключается и восстанавливает поток без неограниченного роста очереди.

## Заполнение хранилища

Проверяйте квоту SQLite и реальное отсутствие свободного места отдельно. Действующие сообщения должны сохраняться; новая отправка должна возвращать `507 storage_full`. После освобождения места отправка должна возобновиться.

Для проверки ENOSPC предусмотрен сценарий с ограниченным tmpfs внутри Docker:

```sh
python3 tools/disk_full.py --help
python3 tools/disk_full.py --binary target/release/poknited \
  --image YOUR_TEST_IMAGE --tmpfs-bytes 524288 \
  --report /tmp/poknite-verification/disk-full.json
```

Образ должен содержать Python 3 и системные библиотеки для выбранной сборки сервера. Используйте отдельный тестовый контейнер. После ошибки проверьте чтение, восстановление потока, повтор существующего идентификатора и целостность базы.

## Настольные клиенты

Проверяйте Windows 10/11 и Ubuntu 24.04 в обычном пользовательском сеансе. На Linux повторите основные сценарии в X11 и Wayland с XWayland, с поддержкой трея и без неё.

1. Подключите клиент и проверьте системное уведомление, русский текст и режим без звука.
2. Закройте окно крестиком и проверьте получение в фоне.
3. Запустите приложение повторно: должен открыться существующий экземпляр.
4. Проверьте автозапуск после входа в систему и завершение через «Выход».
5. Отправьте сообщения во время сна и отключения сети; после восстановления проверьте историю и сводное уведомление.
6. Снимите память с открытым окном и в фоне при активном приёме. Проверьте, что ожидание не вызывает постоянной загрузки CPU.

Отдельные проверки D-Bus требуют `dbus-daemon`, `python3-dbus` и `python3-gi`:

```sh
python3 crates/desktop/tests/dbus_fixture.py
python3 crates/desktop/tests/tray_fixture.py
```

Для автоматической проверки подключённого Linux GUI можно использовать отдельный Xvfb-сеанс и соответствующий `DISPLAY`:

```sh
python3 tools/client_smoke.py --server target/release/poknited \
  --client target/release/poknite \
  --gui-report /tmp/poknite-verification/linux-gui.json
```

Сценарий создаёт собственные сертификаты, пользователей и временную базу. GUI-проверка включает поиск разговоров, переключение двух каналов с разными черновиками, восстановление выбранного канала после полного завершения процесса и отправку восстановленного черновика по Ctrl+Enter. Снимок экрана с тестовыми данными сохраняется рядом с отчётом; нужны libXtst и ffmpeg. Проверка в Xvfb не подтверждает интеграцию с конкретным окружением рабочего стола. На Windows отдельно проверяйте системные уведомления, трей и сохранение токена средствами DPAPI; перекрёстная сборка этого не проверяет.

## Android

Используйте физический телефон с подписанной release-сборкой и действующим HTTPS-соединением. Эмулятор подходит для функциональных тестов, но не для выводов о батарее или работе при выключенном экране.

Проверьте получение с погашенным дисплеем, в Doze, при переходе с Wi-Fi на мобильную сеть, после потери сети, перезагрузки и обновления приложения. После принудительной остановки вновь откройте приложение перед проверкой приёма. Повторите сценарии с обычными настройками батареи и с разрешённой фоновой работой; укажите ограничения производителя.

Проведите два отдельных суточных замера батареи: на Wi-Fi и на мобильной сети. Запишите модель телефона, версию Android, качество сигнала, настройки энергосбережения, число сообщений и включённые фоновые приложения. Для оценки вклада Poknite сравните с контрольным периодом в сопоставимых условиях без приёма.

Для снимка памяти:

```sh
adb shell dumpsys meminfo org.poknite
```

Снимайте PSS с открытым экраном приложения, после сворачивания при активном соединении и после восстановления большой истории. Измерение при выключенном приёме не подтверждает бюджет фоновой службы.

## Публикация результатов

Прикладывайте результаты к соответствующему выпуску вместе с контрольными суммами сборок. Указывайте методику, условия и фактические значения, включая превышения бюджетов и непроверенные платформы. Исходные измерения должны позволять отличить функциональный тест от нагрузочного, эмулятор от физического устройства и локальную сеть от интернета. Не включайте в отчёты токены, приглашения или содержимое пользовательских сообщений.

## Приёмка v2 и RGB

`python3 tools/v2_smoke.py` создаёт отдельную CA, два настоящих HTTPS-слушателя и временный профиль нативного клиента. Он проверяет подключение управления к отдельному IP с сохранением доменного имени TLS, отказ при неверном имени сертификата, отсутствие admin на публичном сервисе, HTTP 426 для v1, проверку реального peer CIDR несмотря на подставленные заголовки, доступность переписки при недоступном управлении. `--gui --report /tmp/poknite-verification/v2.json` в отдельном Xvfb-сеансе дополнительно открывает интерфейс и сохраняет снимок экрана рядом с отчётом; нужен ffmpeg.

Rust-тесты v2 проверяют конфликтующие роли, защиту последнего администратора, ограничение делегирования, приватность и уникальность личных диалогов, общие каналы, Unicode-упоминания/`notify` при повторе и восстановлении, отключение пользователей/устройств/приглашений, закрытие канала, миграцию с резервной копией, постоянный RGB и обновление автора. Большой каталог проверяется на 100 пользователях/64 каналах с сохранением лимита кадра. Клиентские тесты проверяют миграцию истории/курсора/черновика, сохранение цвета и отмену уведомлений при отзыве чтения.

Android JVM-тесты включают границы RGB; instrumentation-тесты — миграцию старой SQLite, RGB в истории, серверный `notify=false` и отмену очереди при потере прав. Они требуют реально запущенного устройства/эмулятора, сборка тестового APK сама по себе их не выполняет. Набор результатов текущей разработки: [проверки 0.2](verification-0.2.md).

## Сквозное шифрование

Rust-тесты проверяют независимый AES-GCM/JWE вектор, подмену шифротекста и метаданных, отсутствие ключа, восстановление истории после импорта, точный повтор конверта, отказ устаревшему составу устройств и недоступность нового ключа исключённому участнику. Серверный интеграционный тест проверяет каналы и личные диалоги, хранение шифротекста, HTTP-повторы, WSS-восстановление и отказ открытой отправке по умолчанию.

`E2eeTest` на Android использует тот же независимый вектор для шифрования и расшифровки, проверяет защищённое сохранение ключа, перезапуск и смену состава. Запуск отдельно от живого сервера:

```sh
adb shell am instrument -w -e class org.poknite.E2eeTest \
  org.poknite.test/org.poknite.TestRunner
```

GUI-сценарий `client_smoke.py --gui-report` также открывает «Шифрование», показывает код тестового разговора и импортирует его обратно. Секретный код не включается в снимок или отчёт. Для подключения реального разговора следуйте [инструкции E2EE](e2ee.md). Результаты текущего прогона: [проверки E2EE](verification-e2ee.md). Функциональные проверки не заменяют независимый аудит криптографического протокола и клиентов.
