# Протокол Poknite v1

Справочник реализованного сервера `poknited`. Источник моделей — `crates/protocol`; все тела запросов и события — JSON UTF-8. Идентификаторы каналов, пользователей, устройств, `seq` и курсоры — целые `i64`, время — секунды Unix UTC. Клиент должен сохранять числа без потери точности.

## Транспорт и доступ

Рабочий транспорт — HTTPS и WSS с проверкой сертификата и имени сервера. `serve --dev-http` разрешает HTTP/WS только при адресе прослушивания на loopback. Сквозного шифрования нет: сервер читает текст сообщений.

Все `/v1` запросы, кроме подключения по приглашению, требуют заголовка `Authorization: Bearer <token>`. Токен устройства — случайные 32 байта в виде 64 шестнадцатеричных символов. Токены не передаются в URL; сервер хранит SHA-256 токенов и приглашений. Ответы обработанных запросов получают `Cache-Control: no-store`.

`GET /healthz` без авторизации возвращает `200` и `{"status":"ok","version":"0.1.0"}`. Это проверка доступности процесса, не отдельная проверка записи на диск.

## REST

Для запросов с телом нужен `Content-Type: application/json`. Успех возвращает JSON с HTTP `200`, кроме отзыва устройства (`204`, пустое тело).

| Метод и путь | Запрос | Ответ |
|---|---|---|
| `POST /v1/devices/enroll` | `{"invitation":"<64 символа>","device_name":"Телефон"}` | `{"token":"<64 символа>","device_id":2,"user_id":1,"user_name":"Анна","retention_seconds":86400}` |
| `GET /v1/channels` | Без тела | `[{"id":1,"name":"Общий"}]` |
| `POST /v1/channels/{id}/messages` | `{"client_message_id":"<UUID>","text":"Привет"}` | Объект сообщения, описанный ниже |
| `GET /v1/devices` | Без тела | `[{"id":2,"name":"Телефон","created_at":1790000000,"current":true}]` |
| `DELETE /v1/devices/{id}` | Без тела | Отзыв собственного активного устройства; можно отозвать текущий токен |
| `GET /v1/stream?after=42` | WebSocket Upgrade, авторизация в заголовке | `101 Switching Protocols`; далее события потока |

Список каналов содержит текущие права пользователя. Список устройств содержит только его активные устройства; `current` отмечает устройство данного токена. Чужой, уже отозванный или отсутствующий идентификатор при `DELETE` возвращает одинаковый `404`.

Приглашение действует 900 секунд и расходуется только при успешной регистрации. Конкурентные регистрации одного приглашения дают одно новое устройство. Ошибка лимита устройств оставляет приглашение действующим до окончания его срока. Токен возвращается только при регистрации: восстановить его из серверной базы нельзя.

Объект сообщения:

```json
{
  "id": "95189a34-26bd-4924-94b9-ac7d5a318be8",
  "seq": 43,
  "channel_id": 1,
  "sender_id": 1,
  "sender_name": "Анна",
  "text": "Привет",
  "created_at": 1790000000,
  "expires_at": 1790086400
}
```

`id` создаёт сервер. `seq` растёт для всей серверной базы, а не отдельно для канала. Отправитель определяется токеном; произвольного `sender_id` в запросе нет. Текст сохраняется без обрезки пробелов и обработки разметки. Он должен содержать непробельный символ, занимать не более 4096 байт UTF-8 и не содержать управляющих символов, кроме `\n`, `\r`, `\t`. Имя устройства, пользователя и канала — непустое после обрезки краёв, до 64 Unicode-символов, без управляющих символов; имя сохраняется с обрезанными краями.

Успех отправки означает, что запись уже зафиксирована в SQLite. Дедупликация действует по паре «устройство + точная строка `client_message_id`». Клиенты используют UUID в обычной форме с дефисами и нижним регистром. Повтор того же идентификатора, канала и текста возвращает исходное сообщение; изменение канала или текста даёт `409 id_conflict`. Пока истёкшая запись ещё физически присутствует, повтор даёт `410 expired`. После удаления записи идентификатор можно использовать снова; клиент должен создавать новый UUID для каждого нового сообщения и хранить прежний UUID только для повторения неопределённой отправки. Доступ к каналу проверяется и для повтора. Сохранённый повтор доступен при заполненном хранилище, если база допускает чтение и короткую транзакцию.

## WebSocket: восстановление и подтверждения

`after` — последний **локально сохранённый** курсор устройства, по умолчанию `0`; отрицательное значение недопустимо. Сервер не заменяет его своим сохранённым ACK. Одно устройство имеет одну активную сессию: новое подключение отменяет прежнее. Разные устройства одного пользователя восстанавливаются независимо.

События сервера — текстовые JSON-кадры:

| `type` | Поля | Значение |
|---|---|---|
| `hello` | `user_id`, `device_id`, `channels:[{id,name}]` | Первое событие; клиент сверяет свою идентичность и обновляет каналы |
| `reset` | `cursor` | Переданный `after` оказался выше серверной позиции; сейчас сервер всегда присылает `cursor:0` |
| `message` | `message:{...}`, `replay:boolean` | Сообщение; `replay:true` относится к начальному восстановлению |
| `progress` | `cursor` | Все доступные сообщения до этой позиции уже отправлены по данному соединению |
| `synced` | `cursor`, `gap:boolean` | Начальное восстановление завершено; далее идут сообщения с `replay:false` |
| `channels` | `channels:[{id,name}]` | Изменён полный список доступных каналов |

Последовательность начала: `hello`, необязательный `reset`, сообщения и `progress`, затем один `synced`. Сервер выбирает сообщения страницами до 50 записей, но каждое сообщение отправляет отдельным событием. Истёкшие сообщения и каналы без прав пропускаются. Поэтому `progress.cursor` может быть выше `seq` последнего видимого сообщения; это нормальная позиция общего потока. Пустое восстановление также заканчивается `synced`.

Единственное текстовое событие клиента:

```json
{"type":"ack","cursor":43}
```

Клиент сначала атомарно сохраняет сообщение и задание уведомления в локальной базе. Получив `progress`, он сохраняет его курсор и отправляет ACK. Получив `synced`, он также сохраняет и подтверждает курсор, затем показывает сводное уведомление для восстановленных сообщений. ACK на каждое отдельное сообщение не требуется. ACK подтверждает сохранение, а не прочтение пользователем или успешный показ системного уведомления. Повторное получение устраняется по серверному `id`.

ACK должен быть неотрицательным и не превышать объявленный сервером курсор данного соединения. Будущая/отрицательная позиция и неправильный JSON закрывают соединение. Повторные и уменьшающиеся ACK не уменьшают серверную позицию и не требуют новой записи. Получив `reset`, клиент сбрасывает только курсор восстановления, сохраняя локальные копии и их идентификаторы для дедупликации. Локальную историю нельзя очищать в ответ на истечение серверного TTL.

`synced.gap:true` означает, что сервер обнаружил недоступные по сроку сообщения после переданной позиции: среди ещё не удалённых записей или в сохранённой отметке потерь устройства. Их текст восстановить нельзя. Флаг не содержит количества пропусков и не является отдельным событием для каждой последующей очистки. Сервер помнит максимальную потерянную позицию, а не журнал всех потерь. При позднем предоставлении доступа уже пройденная общая позиция автоматически не перематывается к старым сообщениям нового канала.

Heartbeat использует стандартные WebSocket Ping/Pong, не JSON: по умолчанию Ping раз в 120 секунд, допустимое ожидание Pong 30 секунд с периодической проверкой. Клиент отвечает Pong с полученными данными. На медленную запись сервер отводит до 5 секунд. Потерянное соединение нужно восстанавливать с локальным курсором и задержкой с нарастающим интервалом и случайным разбросом. При отзыве устройство перестаёт проходить авторизацию; возможен Close `4001` с причиной `revoked`, обычное закрытие или обрыв. Только код `4001` либо HTTP `401` достоверно обозначают отзыв; после обычного обрыва клиент пробует подключиться снова.

## Ограничения и ошибки

Значения по умолчанию: 20 пользователей, 3 активных устройства на пользователя, 60 WebSocket-соединений, 64 канала, 3 действующих приглашения на пользователя, TTL 86400 секунд. Основная база ограничена 32 МиБ с округлением бюджета вниз до страниц 4096 байт. WAL имеет бюджет 4 МиБ: используются автоматические контрольные точки через 64 страницы, проверка журнала перед обычной записью и усечение при обслуживании; размер одного коммита может временно увеличить журнал. Когда журнал достиг бюджета и контрольную точку выполнить нельзя, новые обычные записи отклоняются. При уменьшении бюджета ниже существующей базы запуск отклоняется; сначала нужна очистка со старой конфигурацией.

Очистка раз в 60 секунд удаляет до 256 истёкших сообщений за проход, просроченные приглашения и отозванные устройства без оставшихся ссылок сообщений, затем выполняет небольшое освобождение страниц и контрольную точку WAL. Начиная с `expires_at` текст уже не выдаётся, даже если физическое удаление ещё не выполнено. Смена TTL влияет только на новые сообщения.

HTTP-тело и входящий WebSocket-кадр/сообщение ограничены 32768 байт; одновременно обрабатывается до 128 HTTP-запросов, очередь SQLite — 64 задания. Сверх заполненной очереди база отвечает недоступностью; ожидания не накапливаются без ограничения.

Лимиты в независимых окнах 60 секунд от первого запроса: все HTTP-запросы — 2400 на IP, регистрации — 10 на IP, попытки WebSocket-подключения — 120 на IP, отправка — 30 запросов на устройство, входящие текстовые WebSocket-кадры — 2400 на устройство. Неуспешные и повторные попытки учитываются. Число записей счётчиков ограничено 1024. Перезапуск сбрасывает счётчики. Регистрация множества устройств за одним IP требует учитывать предел 10 в минуту.

Ошибки прикладных обработчиков имеют форму `{"code":"forbidden","message":"Нет доступа к каналу"}`:

| HTTP | `code` | Причина |
|---|---|---|
| `400` | `invalid_input` | Неверное приглашение по длине или имя устройства |
| `400` | `invalid_message` | Неверный UUID или текст |
| `400` | `invalid_cursor` | Отрицательный `after` |
| `401` | `unauthorized` | Нет токена, неверный токен или устройство отозвано |
| `401` | `invalid_invitation` | Приглашение истекло, отсутствует или использовано |
| `403` | `forbidden` | Нет доступа к каналу |
| `404` | `not_found` | Устройство недоступно для отзыва |
| `409` | `device_limit` | Достигнут лимит активных устройств |
| `409` | `id_conflict` | UUID отправки уже связан с другим текстом или каналом |
| `410` | `expired` | Повтор истёкшего сообщения, запись ещё присутствует |
| `429` | `rate_limit` | Превышен лимит частоты или заполнена таблица счётчиков |
| `503` | `request_limit` | Все места HTTP-обработки заняты |
| `503` | `connection_limit` | Нет места для потока за 3 секунды ожидания |
| `503` | `database_unavailable` | База занята, остановлена или недоступна |
| `503` | `stopping` | Семафор подключений закрыт |
| `507` | `storage_full` | Бюджет SQLite/диска исчерпан или WAL нельзя обслужить |

Ошибки разбора пути, query, JSON, заголовков Upgrade и `Content-Type` формирует Axum: это могут быть `400`, `413`, `415`, `422` с текстовым телом, а не `ApiError`. Неизвестный путь даёт `404`, неверный метод — `405`. Клиент должен сохранять устойчивость к ошибкам без JSON и не повторять отправку автоматически после явно подтверждённой ошибки. HTTP `429` не содержит `Retry-After`.

## Локальное администрирование

Общий синтаксис: `poknited --config /путь/poknite.toml КОМАНДА`. Без `--config` читается `poknite.toml` из рабочей директории. CLI запускают с доступом к тому же каталогу данных и тем же пользователем ОС, что и службу. Ошибка завершает команду с ненулевым кодом. Административных REST-методов нет.

| Команда | Результат |
|---|---|
| `init` | Подготовка базы и канала `1` «Общий» |
| `user "Анна"` | Создание пользователя и доступа к каналу `1`; вывод идентификатора |
| `channel "Работа"` | Создание канала; вывод идентификатора |
| `grant USER CHANNEL` | Предоставление пользователю доступа к каналу, повтор безопасен |
| `ungrant USER CHANNEL` | Удаление доступа |
| `invite USER` | Вывод одноразового кода на 15 минут |
| `revoke DEVICE` | Отзыв любого устройства администратором |
| `status` | Счётчики таблиц и список пользователей; число устройств включает отозванные записи до очистки |
| `cleanup` | Один ограниченный проход очистки; вывод числа удалённых сообщений |
| `serve` | Прямой HTTPS/WSS, запуск фонового обслуживания |
| `serve --dev-http` | Только локальная разработка на loopback |

CLI фиксирует изменения через SQLite и затем посылает сигнал пробуждения в приватный Unix-сокет `data_dir/admin.sock`; каталог данных имеет права `0700`, сокет — `0600`. Сервер перепроверяет права живых потоков и отменяет отозванные устройства. Если сервер остановлен, изменения вступают в силу при следующем запуске. Секрет приглашения выводится только локальной командой; нельзя сохранять его в общедоступном журнале.

`SIGTERM`/Ctrl+C запускают завершение с ограничением ожидания 5 секунд. `SIGHUP` в HTTPS-режиме повторно читает конфигурацию и одновременно обновляет сертификат/ключ и TTL после проверки. Прочие параметры требуют перезапуска. Повреждённая, несовместимая, истёкшая или ещё не действующая цепочка/ключ отклоняется; остаётся прежний сертификат и TTL. Существующие соединения сохраняются при успешной ротации.
