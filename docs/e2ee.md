# Сквозное шифрование Poknite

Новые сообщения шифруются на устройстве отправителя и расшифровываются на устройствах участников. Это действует для каналов и личных диалогов. Сервер хранит зашифрованный текст, поэтому доставка после отключения продолжает работать. HTTPS/WSS остаются обязательными.

## Подключение разговора

1. Сначала зарегистрируйте все нужные устройства обычными приглашениями.
2. На одном доверенном устройстве выберите разговор и откройте «Шифрование». На Android этот пункт находится в «Настройках» как «Шифрование текущего разговора».
3. Нажмите «Создать / сменить ключ». Программа создаёт случайный 256-битный ключ на этом устройстве.
4. Передайте показанный код только доверенным участникам через личную встречу или другой защищённый канал. Код содержит секрет: не отправляйте его в открытой переписке, журналах или отчётах об ошибках. Для переноса на новое собственное устройство используйте уже доверенное устройство.
5. На остальных устройствах откройте тот же разговор, вставьте код и нажмите «Подключить код». Сверьте отпечаток ключа с первым устройством.

Приглашение даёт доступ к серверу, но не даёт ключей разговоров. Для одного разговора участники используют один код, созданный на одном из устройств.

При добавлении или отзыве устройства, отключении пользователя или изменении состава читающих участников программа требует новый ключ. Создайте его на доверенном устройстве и перенесите только тем, кому разрешено читать дальнейшую переписку. До этого новая отправка блокируется. Старые ключи сохраняются локально для полученной истории. Исключённый участник сохраняет прежние сообщения и ключи; новый ключ ему передавать нельзя.

Если сообщение получено до подключения ключа, клиент сохраняет шифротекст и показывает значок замка. После подключения подходящего ключа сохранённые сообщения расшифровываются без повторного уведомления. Новый ключ не открывает сообщения, зашифрованные старым ключом. Данные, уже удалённые сервером и не полученные устройством, восстановить нельзя.

## Защита и ограничения

Копия серверной базы новых сообщений не содержит открытого текста и ключей. Администратор сервера без кода ключа не может прочитать новые сообщения, включая пересылку. Изменение шифротекста, защищённых идентификаторов сервера/разговора/автора или упоминаний приводит к отказу проверки подлинности. Клиенты отправляют только зашифрованный текст и не переключаются на открытую отправку при ошибке.

Сервер видит пользователей, устройства, каналы, автора, время, размер сообщения и адресатов упоминаний. Он может задержать или удалить доставку. Администратор, которому участники передали ключ как участнику разговора, может читать этот разговор.

Используется общий ключ разговора. Любой обладатель ключа может читать сообщения, передать ключ другому человеку и создавать корректные криптографические сообщения. Отдельных подписей устройств и независимого криптографического доказательства авторства внутри доверенной группы в этой версии нет; API проверяет авторство по токену устройства. Не считайте её протоколом Signal или MLS.

Автоматического обновления ключа после каждого сообщения (forward secrecy/Double Ratchet) нет. Утечка ключа позволяет расшифровать сохранённый шифротекст, созданный этим ключом. Смена ключа защищает дальнейшие сообщения при условии, что новый ключ не передан исключённому участнику.

Утрата всех устройств и сохранённых кодов означает утрату доступа к зашифрованному тексту. Сервер не может восстановить ключ. Android хранит ключи в зашифрованных настройках, защищённых Android Keystore; Windows использует DPAPI; Linux защищает локальную базу правами пользователя (каталог 0700, база 0600). Локальные тексты истории остаются открытыми. Владелец устройства с достаточным доступом может прочитать локальную историю и используемые ключи.

Обновление не защищает задним числом старые открытые сообщения, SQLite/WAL, резервные копии и ранее выданные клиентские копии. Старые открытые сообщения, присланные сервером после обновления клиента, отображаются как недоступные и не создают текстовых уведомлений. Уже сохранённая локальная история остаётся доступной. Обновляйте сервер и оба клиента совместно.

Сервер по умолчанию требует E2EE (`e2ee_required = true`). `false` предназначено для проверок старого API и временной совместимости: оно разрешает старым клиентам отправлять открытый текст. Новые клиенты при этом продолжают требовать шифрование и отклоняют открытый текст с сервера.

## Формат и проверки

Используется JWE compact serialization [RFC 7516](https://www.rfc-editor.org/rfc/rfc7516.html), `alg=dir`, `enc=A256GCM`: случайный 96-битный nonce, 128-битный тег, AES-256-GCM. Примитив реализуют RustCrypto `aes-gcm` на настольных клиентах и системный `javax.crypto` на Android. В защищённый заголовок включены версия, идентификатор ключа, сервер, разговор, автор, устройство, UUID сообщения, хеш состава устройств и упоминания. Точные байты закодированного заголовка являются associated data. Ключ не передаётся в HTTP/WebSocket API.

Конверт сохраняется локально до отправки HTTP. Повтор того же черновика повторяет байты конверта и UUID; повторная доставка устраняется по защищённым ID устройства и сообщения. Неизвестные шифротексты сохраняются вместе с локальным сообщением до подтверждения курсора. Локальное хранилище ограничено 1024 ключами; при заполнении импорт/создание отклоняются без удаления прежних ключей.

Публичный тестовый вектор в `tools/fixtures/e2ee.json` создан независимой реализацией Python cryptography. Его ключ и nonce предназначены только для тестов. Rust и Android проверяют совместимость, подмену данных, отсутствие ключа, повторные отправки и смену состава устройств. Это функциональные проверки, а не независимый аудит всей реализации.

## Локальная автоматизация

Для тестовой установки доступны команды:

```sh
poknite --headless key-create --channel 1 --key-file /private/channel1.code
poknite --headless key-export --channel 1 --key-file /private/channel1-copy.code
poknite --headless key-import --channel 1 --key-file /private/channel1.code
```

Создание и экспорт требуют нового файла; существующий файл не перезаписывается. В Linux он создаётся с правами 0600. Команды не печатают код ключа в stdout. Переносите файл только между доверенными устройствами и храните защищённо. Для собственного CA, отдельного профиля и тестового loopback используйте обычные параметры клиента.
