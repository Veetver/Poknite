# Управление из доверенной сети

Сетевое управление по умолчанию выключено. Публичный HTTPS обслуживает переписку; административный HTTPS слушает другой порт и проверяет реальный адрес соединения, токен устройства и права роли. Poknite использует обычную маршрутизацию LAN/VPN; определять или устанавливать конкретную VPN не требуется.

## Настройка сервера

Чтобы включить только локальный доступ, добавьте в `/etc/poknite/poknite.toml`:

```toml
[management]
enabled = true
listen = "127.0.0.1:8444"
allowed_subnets = ["127.0.0.0/8", "::1/128"]
```

Для доступа из выбранной LAN или сети VPN задайте конкретный адрес интерфейса сервера и явные CIDR. Пример адресов документации — замените их адресами своей сети:

```toml
[management]
enabled = true
listen = "10.70.0.1:8444"
allowed_subnets = ["10.70.0.0/24", "fd70:70::/64"]
```

В IPv6 адрес слушателя записывается как `[fd70:70::1]:8444`. Один слушатель имеет один конкретный адрес; `0.0.0.0`, `::` и CIDR `/0` отклоняются. Адрес слушателя должен входить в выбранную подсеть. Сервис использует тот же проверенный TLS-сертификат и ключ; административное доменное имя должно быть в сертификате. Даже при публичном локальном тестовом HTTP управление требует TLS.

Firewall разрешает административный порт только из выбранных подсетей. Для UFW пример IPv4, если этот адрес и диапазон соответствуют вашей конфигурации:

```sh
sudo ufw allow proto tcp from 10.70.0.0/24 to 10.70.0.1 port 8444
sudo ufw deny proto tcp to 10.70.0.1 port 8444
```

Сначала проверьте порядок и уже имеющиеся правила (`sudo ufw status numbered`): широкое прежнее разрешение может открыть порт раньше запрета. Для IPv6 используйте соответствующие адреса и включённую поддержку IPv6 firewall. Сетевые правила/маршруты настраивает администратор инфраструктуры. Не добавляйте административный порт в публичный reverse proxy, NAT или проброс маршрутизатора. За reverse proxy проверяется адрес самого прокси; присланный заголовок IP не заменяет проверку реального peer.

Перезапустите службу после настройки и назначьте первого администратора локальной командой:

```sh
sudo systemctl restart poknite
sudo -u poknite poknited --config /etc/poknite/poknite.toml administrator 1
sudo -u poknite poknited --config /etc/poknite/poknite.toml invite 1
```

Замените `1` ID нужного пользователя. Подключите устройство приглашением к публичному адресу переписки, затем откройте «Управление». Локальные команды остаются доступны, когда сетевое управление выключено.

## Настройка клиента

Укажите отдельный HTTPS-адрес управления, например `https://chat.example.org:8444`. Если публичный DNS ведёт на внешний адрес, в поле «IP подключения» можно указать `10.70.0.1`: только административные запросы идут к нему, домен `chat.example.org` сохраняется для TLS и Host, DNS переписки остаётся обычным. При недоступности адреса клиент сообщает «Управление недоступно из текущей сети». Управление не переходит на публичный адрес и не останавливает публичную переписку.

Из управления можно создавать пользователей, выбирать их роли и RGB, выдавать/отзывать приглашения и устройства, создавать/переименовывать/закрывать каналы и редактировать групповые правила. Пользователь может иметь несколько ролей: запрет перекрывает разрешения остальных ролей. Создавайте дополнительную роль для делегирования только нужных действий. Последнего администратора защищает сервер.

Контакты содержат пользователей общих открытых каналов. Выбор контакта открывает единственный личный диалог пары. После исчезновения общих каналов остаётся история, отправка прекращается. Через приложение администратор не читает чужие личные диалоги. Новые сообщения защищены [сквозным шифрованием](e2ee.md): оператор серверной базы видит шифротекст и метаданные, а для чтения требуется ключ с доверенного устройства. Старые открытые сообщения и резервные копии сохраняют прежний уровень защиты.

## Обновление с 0.1

Остановите сервер, сохраните его конфигурацию и доступные резервные копии, обновите сервер и все клиенты до 0.2. Сервер при первом запуске сам сохраняет согласованную копию v1, затем мигрирует базу транзакционно. Старые токены/ID/история/курсор/черновики сохраняются. Пользователи получают роль «Участник» и случайный постоянный цвет; прежние персональные разрешения каналов сохраняются. Назначьте администратора командой выше. Старый API возвращает требование обновления.

Откат сервера до 0.1 требует остановленной службы и восстановления сохранённой v1-копии; новая база более старой версией не открывается. Новые сообщения, появившиеся после резервной копии, в неё не входят. Клиентские локальные копии сохраняются независимо от server TTL.
